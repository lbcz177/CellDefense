## 每次操作顺序

1. 核对当前 CLI 帮助与目标方法 schema，登录后只读查询目标游戏和现有资料 / 包体状态。
2. 本地保存原资料快照，准备本次拟修改内容、APK 版本 / 摘要及素材列表，展示前后差异。
3. 询问用户确认具体字段、文件和操作范围；未确认时保留本地草稿。
4. 执行已确认范围，回读平台状态，记录版本、变更和结果。
5. 提审和公开上线单独确认；需要立即上线或定时上线时，明确展示对应时间安排。

确认发布文案不代表确认上传包体或提审；确认上传包体不代表确认上线。后续改变已展示的内容时重新确认。

## CLI 准备与调用

项目内工具位置为 Tools/TapTapCLI，依赖版本锁定在 package.json / package-lock.json；依赖目录不提交。使用本地入口，避免修改全局 npm 配置：

~~~powershell
& ./Tools/TapTapCLI/node_modules/.bin/taptap-cli.cmd version
& ./Tools/TapTapCLI/node_modules/.bin/taptap-cli.cmd --help
& ./Tools/TapTapCLI/node_modules/.bin/taptap-cli.cmd auth login --no-wait --json
~~~

登录由用户在官方页面完成，凭据不写入仓库。登录之后才可读取账号范围内的厂商和游戏资料；不能仅凭后台链接推定账号已授权。

根据[官方 CLI 文档](https://developer.taptap.cn/v3/cli/)，可使用 developer +list、app +list 定位对象，app analyze-app-status 查看资料和发布缺口。每次业务调用前核对当前安装版本的 schema；本地文件上传也属于写操作，使用 dry-run 预览后等待用户确认，再正式执行。

只有用户明确要求提审时才准备审核快照；后续预检与正式提交按当时 schema 核对同一目标版本和上线安排。网站概览和当前 CLI 细则对审核请求字段的描述存在差异，因此不硬编码 review_fingerprint 等字段，实际操作前重新读取 schema，严禁自行补字段。预检后展示结果并取得最终确认。写入结果不明时先回读状态，保留原幂等键，避免重复提交。

此文档不把候选包视为已发布版本，也不预设平台审核结论。

## 登录后的操作顺序

1. 用户表示准备登录后，Agent 执行 auth login --no-wait --json，原样交付 verification_url；使用完整 device_code、expires_at、interval 恢复轮询。授权数据仅在内存中使用，不写入仓库或日志。
2. 授权成功后直接以已知厂商 / App ID 查询资料和版本；先分析当前状态，再读取返回的真实模块和版本数据，保存本次原资料快照。无需重复搜索用户已明确提供的 ID。
3. 展示当前平台内容与 当前候选文案 / 包体差异，等用户确认具体范围。旧包名相同不代表平台已接受新包；如平台已有更高版本，先告知用户，重新准备合适的候选。
4. 只执行已确认动作；上传 APK、绑定资料页包体、修改文案是不同动作。提审与上线仍需单独确认。
